### 1. Invoice A/R posting error is swallowed — invoice marked "sent" with no ledger entry

- **Where:** `src/routes/api/-invoices.ts:825` — accounting-correctness
- **Verdict:** CONFIRMED
- **What:** Invoice A/R posting error is swallowed — invoice marked "sent" with no ledger entry. In transitionInvoiceStatus (src/routes/api/-invoices.ts), updateFields.status is set to the new status at lines 795-798, before the SENT branch attempts posting. The SENT branch (lines 808-832) wraps createArJournalEntry in try/catch; the catch at line 825 treats ANY throw as non-fatal (logs via logger.error, line 827, then falls through). The unconditional invoice update at lines 935-939 then commits status='sent' with journalHeaderId=null. This swallows every fail-closed guard inside createArJournalEntry: period-lock (509-513), missing Sales Tax Payable account via resolveTaxPayableAccount (442-446), missing discount account via resolveDiscountAccount (466-470), partial revenue-account assignment (549-555), and the validateBalance imbalance check (602-608). Because getArAging (src/routes/api/-reports.ts:161) includes status 'sent'/'viewed'/'overdue'/'partial' and reports balanceDue without any join to posted journal lines, the invoice enters A/R aging and the dashboard while nothing is posted to the general ledger, so the A/R subledger permanently diverges from the balance-sheet A/R line. The divergence is permanent: VALID_TRANSITIONS (385-391) has no sent->sent edge and createArJournalEntry is only reachable from the SENT branch gated on !journalHeaderId, so the journal can never be posted for that invoice; a later paid/partial transition even credits A/R that was never debited. Failure scenario: a new org sends a $50-tax invoice with no 'Sales Tax Payable' liability account — resolveTaxPayableAccount throws, the catch swallows it, status becomes 'sent' with journalHeaderId=null, aging/dashboard show the balance, trial balance shows nothing, and the user gets no error. Fix: do not swallow; let createArJournalEntry throw propagate so the transition is rejected/rolled back. If a "no revenue accounts yet" path is desired, gate it explicitly and still surface a clear error for the throwing cases (locked period, missing tax/discount account, imbalance, partial assignment). Severity high (not critical): requires a specific misconfiguration/locked-period/partial-assignment to trigger and does not cross tenants or corrupt already-correct data, but it is a silent, permanent GL-vs-subledger divergence with no user-facing error in a multi-tenant accounting app.
- **Failure scenario:** Invoice with a $50 tax line is sent in an org that has no 'Sales Tax Payable' liability account. createArJournalEntry throws 'No Sales Tax Payable account found', the catch swallows it, invoice.status becomes 'sent' with journalHeaderId=null. AR aging and dashboard show the invoice balance; trial balance / balance-sheet A/R shows nothing. Books no longer tie out and the user got no error.
- **Fix:** Do not swallow the error: let createArJournalEntry throw propagate (as sendInvoiceEmailFn already does at line ~1168) so the status transition is rolled back / rejected. If a graceful 'no revenue accounts yet' path is desired, gate the status change on a successful (or explicitly-null) posting and surface a clear error for the throwing cases (locked period, missing tax/discount account, imbalance, partial assignment) instead of marking the invoice sent.

### 2. Cross-org IDOR: batch delete removes another org's journal_lines (no org scope)

- **Where:** `src/routes/api/transactions/-_batch.ts:387` — authz-isolation
- **Verdict:** CONFIRMED
- **What:** Cross-org IDOR: batch delete removes another org's journal_lines (no org scope). - **Failure scenario:** Authenticated user with journal:delete permission in org A calls deleteTransactionsBatch with `ids` = org B's journal_header UUIDs (obtainable/guessable). The header select returns no rows (org A filter) so the period-lock check passes; if org B's txns aren't in a finalized reconciliation the guard passes too. Also scope the reconciliation-guard join by `eq(reconciliations.organizationId, orgId)`.

### 3. Card/PayPal payment idempotency guard is a check-then-act race with no backing unique constraint

- **Where:** `src/lib/invoice-payments.ts:128` — idempotency
- **Verdict:** CONFIRMED
- **What:** Card/PayPal payment idempotency guard is a check-then-act race with no backing unique constraint (src/lib/invoice-payments.ts:128, recordCardInvoicePayment). The idempotency SELECT against journal_headers matching (organizationId, sourceDocumentId, sourceDocumentType='invoice', referenceNumber=externalRef) runs at the default READ COMMITTED isolation, so a concurrent transaction's uncommitted INSERT (line 168) is invisible. No unique constraint or index backs this column combination — migration drizzle/0015 adds only journal_headers_org_transaction_number_unique on (organization_id, transaction_number). Each concurrent call allocates a distinct transaction_number, so both header INSERTs commit and both increment invoices.amountPaid, double-counting the payment and over-reducing A/R. NOTE: the transaction-number sequence allocator (src/lib/sequence.ts allocateSequenceValue, INSERT..ON CONFLICT DO UPDATE on the shared journal:{orgId} row) row-locks and serializes the two transactions, but this does NOT close the race because the idempotency SELECT (line 128) completes before the sequence lock is acquired (line 167) and READ COMMITTED does not re-execute it after the lock is released. Reachable via overlapping duplicate Stripe checkout.session.completed deliveries (handler 500s to force retries) for one payment_intent, or multiple app instances; the PayPal capture path is partially shielded by PayPal's own capture idempotency. Fix: add a partial unique index on journal_headers (organization_id, source_document_id, source_document_type, reference_number) WHERE reference_number IS NOT NULL, and wrap the header INSERT in onConflictDoNothing()/catch the unique-violation so the loser returns alreadyRecorded=true instead of posting. Severity: high — silent corruption of the general ledger and invoice balances in a multi-tenant accounting app, on a function documented as safe to call more than once.
- **Failure scenario:** Stripe (or PayPal) delivers checkout.session.completed twice concurrently for the same payment_intent (webhook retries can overlap). Both invocations of recordCardInvoicePayment run their idempotency SELECT before either commits; both find no existing row; both post a DR-deposit/CR-A/R journal and both add `amount` to amountPaid. A $100 invoice is recorded as $200 paid, A/R is over-reduced, and the GL contains two payment entries for one real payment.
- **Fix:** Add a partial unique index on journal_headers (organization_id, source_document_id, source_document_type, reference_number) WHERE reference_number IS NOT NULL, and wrap the INSERT in onConflictDoNothing()/catch of the unique-violation so the second writer detects the duplicate and returns alreadyRecorded=true instead of posting. A DB-level unique constraint is required — the SELECT-then-INSERT check alone cannot be made race-safe under READ COMMITTED.

### 4. Lost update on invoice amountPaid/balanceDue — read-modify-write with no row lock

- **Where:** `src/lib/invoice-payments.ts:209` — concurrency
- **Verdict:** CONFIRMED
- **What:** Lost update on invoice amountPaid/balanceDue — read-modify-write with absolute writes and no row lock. recordCardInvoicePayment (src/lib/invoice-payments.ts) reads invoice.amountPaid via a plain SELECT (lines 108-120, not FOR UPDATE) inside a READ COMMITTED transaction, computes newPaid = prevPaid + amount (lines 209-210), and writes the absolute value newPaid.toFixed(2) at the UPDATE (lines 214-224) rather than amountPaid = amountPaid + amount. The manual path transitionInvoiceStatus (src/routes/api/-invoices.ts) repeats the pattern (read at 779/841, compute at 867, absolute write at 880, UPDATE at 935-939) and is additionally NOT wrapped in a transaction and has no externalRef idempotency. Because the per-capture idempotency guard only dedupes identical externalRefs, two concurrent DISTINCT payments on the same invoice (e.g. a card-capture webhook and a manual mark-partial, or two partial captures) both read the same prevPaid; the second UPDATE's row lock serializes the write but still stores its stale precomputed absolute value, clobbering the first. Both payment journals are posted, so the GL total exceeds the invoice's recorded amountPaid — a permanent, silent subledger-vs-ledger discrepancy. The overpayment guard in transitionInvoiceStatus (lines 860-865) is computed from the same stale snapshot and can likewise be bypassed by a concurrent writer. Fix: SELECT the invoice row FOR UPDATE at the start of both paths (and wrap the manual path in a transaction), OR update with a SQL expression (amountPaid = invoices.amountPaid + amount) deriving status/balanceDue from the returned value, and re-evaluate the overpayment check against the locked/fresh value. Severity high: reachability requires two concurrent writers on the same invoice within a short window (realistically an automated webhook racing a manual action, or a double-submit), which is uncommon but genuine, and the impact is silent permanent corruption of financial records in a multi-tenant ledger.
- **Failure scenario:** Invoice total $150. A $100 card payment and a $50 manual partial payment are recorded concurrently. Both read prevPaid=0. Card tx writes amountPaid=100; manual tx (row lock serializes the UPDATE, but it still writes its own precomputed value) writes amountPaid=50, clobbering the 100. Final invoice shows amountPaid=50 while the GL contains BOTH payment journals totalling $150 — invoice and ledger permanently disagree. The overpayment guard in transitionInvoiceStatus (-invoices.ts) is likewise computed from a stale snapshot and can be bypassed by a concurrent card payment.
- **Fix:** SELECT the invoice row FOR UPDATE at the start of both paths so concurrent writers serialize on it, OR perform the update with a SQL expression (amountPaid = invoices.amountPaid + amount) and derive status/balanceDue from the returned value. Recompute the overpayment check against the locked/fresh value, not the pre-lock snapshot.

### 8. Reconciliation agent: per-step try/catch inside one surrounding transaction gives false success and silently rolls back all work

- **Where:** `src/routes/api/reconciliations/-_agent.ts:326` — transactionality
- **Verdict:** CONFIRMED
- **What:** Reconciliation agent (src/routes/api/reconciliations/-\_agent.ts, runAgentOnReconciliation): the entire plan.steps loop executes inside a single Postgres transaction. withMutationPermissionOrgContext -> withOrgContext (src/db/index.ts:61-78) runs the handler inside db.transaction(async (tx) => fn(tx)); the injected `db` is that tx executor, and the loop performs no nested tx.transaction/SAVEPOINT. Each step is wrapped in a try/catch (line 326) that logs and continues, with executedCount incremented per step (e.g. lines 260, 279, 308). Because Postgres puts the whole transaction into an aborted state on the first statement error, every subsequent statement fails with 'current transaction is aborted' (also swallowed by the catch); when fn returns, the wrapper's COMMIT is converted to ROLLBACK, so the handler returns {...plan, executedCount} reporting success while the database discards ALL work in the run — matches not applied, reconciliation not finalized, and the per-step activity-log inserts (line 314) rolled back. The per-step try/catch therefore cannot deliver partial-success semantics; it manufactures a misleading success report over an all-or-nothing rollback. Realistic triggers for the initial error: FK violation on statementLines.matchedJournalLineId -> journalLines.id (schema line 146/253) when an AI-planned journalLineId is stale/hallucinated/concurrently deleted; numeric overflow on matchConfidence (decimal(5,2)); or transient lock/serialization errors under concurrency. Correction to the original report: the finalized uuid-literal bug is already fixed (finalize uses userId), and appliedById/actorId are text columns, so the 'ai-agent' literal writes do NOT themselves abort the transaction — the poisoning must come from a genuine DB error on the paths above. Impact is a false success report on a financial reconciliation with no audit trail, conditional on a step error (not the normal path); the transaction rolls back cleanly with no partial/corrupt writes, so severity is medium. Fix: run each step in its own tx.transaction/SAVEPOINT (or its own transaction) so a failed step rolls back without poisoning the rest and only committed steps are counted, or drop the per-step catch and fail the request atomically on any step error.
- **Failure scenario:** An apply_suggestion or dismiss_suggestion step hits any DB error (constraint, transient, or a poisoned prior statement). The transaction aborts; the finalize step and all activity-log inserts then fail silently; the surrounding transaction rolls back on commit. The user receives a response saying e.g. 'N suggestions auto-applied, reconciliation finalized' but the database state is unchanged — matches not applied, reconciliation not finalized, no activity logs written.
- **Fix:** Either drop the per-step try/catch and let the whole plan be atomic (fail the request on any step error), or run each step in its own transaction/savepoint (tx.transaction / SAVEPOINT) so a failed step can be rolled back to a savepoint without poisoning the rest, and only count/report steps that actually committed.

### 40. Dev-login OTP lookup uses LIKE '%email%' substring match, risking the wrong verification row

- **Where:** `server/routes/api/dev/login.post.ts:84` — robustness
- **Verdict:** CONFIRMED
- **What:** Dev-login OTP lookup uses a substring LIKE match risking the wrong verification row (server/routes/api/dev/login.post.ts:84).
