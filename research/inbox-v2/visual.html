3 · The sorter

Jev is the fast brain. It says how sure it is.

Jev answers quickly and cheaply. When it is sure, the row shows up already filled in. When it is not sure, a bigger model tries, and if that is still unsure, you pick. Being sure is not enough to approve. That is the next section.

0.85

Jev is sure → row arrives filled in

Jev is unsure → bigger model, then you

Example papers and made-up confidence numbers. Drag the line and watch where they go.

Two things the code already decides for Jev. First, document reading (OCR) is locked to Gemini, because redaction cannot clean raw document bytes. So Jev should sort the text after OCR, not the PDF itself, unless you choose to change that rule. Second, the code today says "categorize" can never be applied by a model alone. Letting Jev approve means changing that rule on purpose. The next section shows how to do it safely.

Jev only sees text after personal details are masked, and only for orgs that opted in to sending data to it. I could not check Jev's actual API. This design only assumes it takes text and returns a label plus a 0 to 1 confidence. Adding it means a fourth provider next to Gemini, OpenAI, and Anthropic, then putting it first in the sorting chain.

4 · Before Jev can sort

Jev picks from your lists. It never makes up a category.

Sorting means "which of your categories" and "which of your vendors". So the lists come first. When Jev cannot find a fit, the paper still lands, and it lands where you will see it.

Why a fallback, not an error
  • The paper is saved and waiting. Nothing is lost because a category is missing.
  • Uncategorized is always a stop-level fix, so Jev can never approve it.
  • This already works. Every chart preset has Uncategorized accounts, and the "uncategorized" rule already blocks approval.
Jev may suggest, not create
  • If many papers land in Uncategorized, Jev can say "you may want a category called Software subscriptions".
  • You create it with the normal account screen. Creating accounts stays a human job in the code today.
  • Then "Remember this?" ties that vendor to the new category.

Vendors and customers

Jev is a good fit here. Today the check is an exact name match, with no model at all. "MERALCO INC" and "Manila Electric Company" count as strangers. Jev can tell they are the same company for much less than the big model costs.

5 · When Jev presses Approve

Jev earns the button, one kind of paper at a time.

Think of a new bookkeeper. First they watch. Then they suggest. Then they may approve small, boring bills from vendors they know. They lose that job the moment they start making mistakes.

level 0👀 WatchJev writes down "I would approve this". You decide. We count how often you agreed.
level 1💡 SuggestRows show "Jev would approve". You still press the button.
level 2✅ Approve easy onesFor one vendor + kind (say, Meralco bills), Jev approves. Unlocked by an admin.
auto⬇️ Step downIf you start undoing Jev, it drops back to Suggest by itself.
Jev may approve only when all are true
  • This vendor + kind has earned level 2 for this org.
  • Jev is above the "sure enough" line for this paper.
  • No stop-level finding is open.
  • Amount is under the org's limit.
  • Lines balance to the cent.
Always goes to you
  • A new vendor or customer Jev has never seen.
  • A possible duplicate.
  • A date in a closed period, or a different period than usual.
  • Anything that failed to read.
  • A bill that changes a vendor's bank or payment details.
  • Bank matching and splits. These walls stay.

🎲 Spot check1 in 10 is held back for you before it posts

The spot check matters. Today, a human approval is also the "right answer" that trains the test pile. If Jev approves everything, that signal stops. So Jev holds back 1 in 10 of the papers it would approve, before posting, and you decide those. Nothing has to be undone, and your answer is a fair test of Jev.

Most of this ladder already exists in src/lib/ai/autonomy.ts. It asks for 200 reviewed suggestions at 98% agreement before unlocking. It steps down automatically below 95% over the last 50. An admin must flip it on, and no background job can. What is new is a lane per vendor + kind, and inbox approval joining the allowed list.

6 · When you fix something, it sticks

Fix it once. The same paper gets the same answer every time after.

A model cannot promise 100%. A written-down rule can. So your fix does not only "teach" Jev. It becomes a small memory the harness checks before asking Jev. If the memory matches, Jev is not guessing. The answer is looked up.

1 · Jev guesses Grab · ₱386.00
JevAccount: 6200 Travelsure: 0.78

You change it to 6250 Meals. It was a GrabFood order.

2 · "Remember this for next time?"

Same kind of paper, same answer. Jev ran only in the background to compare.

Three layers. Only the first one is a promise.

What "the same paper" means

  • Same file. Identical bytes. The safest match.
  • Same sender + vendor ID. For example the vendor's email address plus TIN.
  • Same vendor name, after cleanup. "MERALCO INC" and "Meralco" count as one.
  • Same words on a line, like "GrabFood". This only picks the account.

You pick how wide when you save. The box shows how many past papers it would have changed, so a too-wide memory is obvious before it exists.

Keeping memories honest

  • Two memories disagree: the paper goes to you. Nobody guesses.
  • Each memory shows how often it was used and how often it was undone.
  • Undone twice in a row: it turns itself off and asks you.
  • A memory belongs to one org, and it lives in the rule pack. You can replay it, roll it back, and see who made it.

Parts exist on v2. Your corrections are saved. A reflection job proposes lessons that an admin approves, capped at 10 lessons per task. Vendor aliases already map a cleaned-up name to a vendor, but only bank matching uses them today. Corrections can become test cases. The missing piece is the Memory layer, checked before the model, and the "Remember this?" step.

7 · Rules that can grow

A rulebook with page numbers. Try a new page in secret first.

If the old scoring works badly with Jev, you do not rip it out. You write a new version of the rule pack and let it run silently next to the old one. You compare. Then you switch.

step 1✏️ WriteRule pack v4: lower the "low confidence" line, add a new check.
step 2🧪 ReplayRun v4 on the practice pile of past papers with known right answers.
step 3👻 Shadowv4 runs on real mail too, but only v3's flags show. v4's are logged.
step 4✅ PromoteIf the scorecard wins, flip the routine to v4. Keep v3 to roll back.

Rules already carry a formula_version, and changing one already requires a reviewed migration. A rule pack is that same idea for a whole set of rules at once, pinned per routine.

9 · The screen

The Inbox only holds what needs you. Everything else is already in the books.

There is no Done folder. Once a paper is approved, by you or by Jev, it is a real bill, expense, or journal entry. You find it where you already look: Bills, Transactions, the ledger. The Inbox empties out. Empty is the goal.

These are filters on one list, not places things go.

The reading pane is a form you already have

An inbox item is an unsaved draft of an existing screen, filled in by memory or Jev. Approve is that screen's Save button. The Inbox does not get its own editor, and it does not get its own way of posting.

  • Where the answer came from: Remembered or Jev with how sure.

Found while checking this. Today, approving an inbox bill writes a journal entry directly. It fills in a bill record only when one already existed. So a bill that arrives by email is posted, but no bill record is created, which means it is missing from the Bills list. If Approve used the Bills editor's own Save, that gap would close on its own.

10 · Review of the three pasted plans

Right direction. A few wrong details.

Agree

One queue, one primary action. Hide Review Agents from the sidebar. Move email setup out of the Inbox. Drop the jargon.

Drop

No Done folder at all. The plans proposed "Needs you | Done". Approved work is already in the ledger, so a Done folder copies Transactions badly. The Inbox is only what needs you.

Fix

"Failed" must show as needing you. The plan maps failed with approved and rejected. A failed paper is exactly one that needs you. It raises a blocking "source processing failed" finding today.

src/lib/inbox/types.ts lists failed outside the open states

Fix

"Behavior unchanged, correctness 5/5" is too generous. Killing the Review Agents page also removes the only screen that turns rules on or off and sets stop versus warn per org. It also removes the scan of already-posted books. Both need a new home before the page goes, or they become database-only.

review_rule_configs holds enabled and impact per org

Rethink

Do not spend P1 polishing the old page. You said the pipeline gets replaced. P0 (hide the nav, redirect) is cheap and worth doing now. The new screen should be built once, on the new routine spine, not twice.

Add

Reuse the existing editors, and their Save. The plans redesign the detail pane as a new "compact editor". Bills, Pay in/out, Transfer, Journal, and Invoice editors already exist. The pane should open the matching one prefilled. Approve should call that editor's save, not a separate inbox posting path.

approveInboxItem in src/lib/inbox/service.ts writes journal_headers directly

Decide

Jev approving means lifting a wall on purpose. Today "categorize" can never be model-applied, at any accuracy, and inbox approval picks accounts. You have chosen to let Jev approve. Do it through the earned-autonomy ladder in section 4, as a reviewed change with its own tests. Do not do it as a config flag.

Add

The plans have no way to test rules. Your real goal is "evolve the rules and prove it". That needs the rule pack version, the replay, and the scorecard. None of the three plans mention them.

Watch

Confidence has a trap. The app treats a bare 1 as 1%, not 100%, unless the schema pins the 0 to 1 scale. Pin Jev's output schema to 0 to 1 so a sure answer is not read as a guess.

11 · What seven reviewers changed

Seven reviewers, one angle each. Here is what moved.

Each one read the real code from one side: screen, intake, posting, Jev, rules, security, rollout. These are the changes that mattered.

Posting

One save path for everyone

The editors' save buttons need a logged-in person, and Jev has none. So the saving code moves into shared "cores" that the editors, the Inbox, and Jev all call. This also fixes the missing bill records, even in today's Inbox.

Audit

Jev needs a name in the log

Today every approval must point at a real user. The log gets an "actor type" so it can say "approved by Jev, lane Meralco bills, sure 0.97, rules snapshot 12".

Screen

Editors become parts, not pages

The Bills and New transaction screens jump away after saving. They get split into components that take a draft and a save action. The pages keep using the same parts. Keys j/k/a/r and auto-advance make clearing fast.

Rules

Rules read a frozen snapshot

Inbox rules read live settings today, the same settings Review Agents edits. So those settings move to Settings first. Routines then pin a frozen snapshot, which makes replay and rollback exact.

Jev

Two small questions, not one big one

First "what kind of paper", then "which of your ~120 categories". Thresholds come from how often Jev was actually right at each confidence level, not from what it says.

Security

Bank details never change by themselves

A bill that changes a vendor's bank account is the classic fraud trick. It always goes to a person. Memories need posting rights, webhooks are signed, and background jobs read the org from the routine itself.

Intake

Simple schedules, loud failures

"Hourly, daily at 6am, weekly" instead of free cron, so no new library is needed. Skipped duplicates get logged. A missing worker secret stops startup instead of silently doing nothing.

Undo

Undo already exists

The code already has "amend by reversal": the original stays, and a mirror entry cancels it. Undoing a Jev approval uses that, which stays safe even after a period is filed.

Every claim, and the ones I overruled, are in research/inbox-v2/review-findings.md on the research branch.
