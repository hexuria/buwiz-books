# Plan: White-label + per-client deployment to each client's own GCP (Model C)

## Context

We want to sell this accounting app to client companies and deploy a **separate, isolated
instance into each client's own Google Cloud project** — compute (Cloud Run), database
(**Cloud SQL for PostgreSQL**), secrets, and storage all living inside the client's GCP.
The operator workflow must be: **clone repo → init for client → setup → deploy**, repeatable
in minutes.

A previous agent built the **opposite** architecture (Model A: one shared Cloud Run + one
shared Neon DB, tenants separated by `Host` header). That code is the wrong model for our
goal, is **dead/unused**, contains a bug, and is **entirely uncommitted**. Decision: **full
clean revert**, then build Model C fresh.

Today's DB is Neon via the generic `postgres-js` driver (`src/db/index.ts`, `DATABASE_URL`),
so switching to Cloud SQL is a connection-string/connectivity change, not a driver rewrite.

## Phase 1 — Per-deployment branding (the actual white-label)

In Model C each deployment serves ONE client, so branding is **per-deployment config**, not a
DB table. No `tenants` table.

**Brand config is split by runtime** (this is the key correction):

- New `src/config/brand.ts` exposing one `brand` object, read from **two sources**:
  - **Client UI** (bundled, build-time): `import.meta.env.VITE_APP_NAME`, `VITE_BRAND_PRIMARY`,
    `VITE_BRAND_ACCENT`, `VITE_BRAND_LOGO_URL`, `VITE_BRAND_FAVICON_URL`, `VITE_SUPPORT_EMAIL`.

  and the root route `<head>` (`src/routes/__root.tsx` title + favicon) + `public/manifest.json`.

- Replace the real brand strings. Confirmed `Buwiz Books` sites (~20), grouped:
  - **Hard platform brand → `brand.appName`:** `src/routes/__root.tsx:29` (title),

## Phase 2 — Cloud SQL connectivity

- `src/db/index.ts`: keep `postgres-js`. Support Cloud SQL Unix socket connection. Cloud Run
  reaches Cloud SQL via a Unix socket at `/cloudsql/PROJECT:REGION:INSTANCE`; `DATABASE_URL`
  form: `postgresql://USER:PASS@/DBNAME?host=/cloudsql/PROJECT:REGION:INSTANCE`. Confirm
  `postgres()` honors the `host=` socket param (it does; otherwise pass `{ host, path }`).
- `drizzle.config.ts` already uses `process.env.DATABASE_URL` — unchanged; it runs against
  whatever `DATABASE_URL` points to (the Auth Proxy in Phase 5).
- RLS (`withOrgContext` in `src/db/index.ts`, `drizzle/rls_policies.sql`) is unchanged and
  still applies inside the client DB.

## Phase 3 — GCP + Cloud SQL provisioning script (fresh)

New `scripts/provision-gcp.sh` (idempotent), run once per client GCP project. Reads
`GCP_PROJECT_ID`, `GCP_REGION`, `SERVICE_NAME`, `DB_INSTANCE`, `DB_NAME` from env/.env:

1. Enable APIs: `run`, `sqladmin`, `artifactregistry`, `secretmanager`, `cloudbuild`.
2. Create Artifact Registry Docker repo.
3. Create **Cloud SQL Postgres** instance (smallest tier default), a database, and an app DB
   user with a generated password.
4. Create runtime **service account** with roles: `run.invoker`, `cloudsql.client`,
   `secretmanager.secretAccessor`, `artifactregistry.reader`; grant Cloud Build SA
   `run.admin` + `iam.serviceAccountUser`.
5. Create Secret Manager secrets: `database-url`, `better-auth-secret`, plus placeholders for
   `gemini`, `resend`, `google-oauth`, storage creds. Print commands to populate values.

## Phase 4 — "Init for a new client" script (clone → init)

New `scripts/new-client.sh` (interactive): prompts for client name, slug, domain,
`GCP_PROJECT_ID`, region, branding (app name/color/logo/support email), then:

- Generates a gitignored `.env` (operator vars: GCP project, region, gcloud config name,
  `DATABASE_URL`, `VITE_*` branding, plus server `APP_NAME`/`MAIL_FROM`/`SUPPORT_EMAIL`) and
  `.env.cloudrun.yaml` (Cloud Run runtime env, secret refs).
- Creates a dedicated gcloud config: `gcloud config configurations create <client>`.
- Prints the next commands (`make provision`, `make deploy`, `make migrate`, `make domain`).

This is the single entry point after cloning.

## Phase 5 — Deploy + migrate (rebuild Makefile targets)

New Makefile targets (keep the existing `_gcp_guard` pattern from HEAD):

- `make provision` → `scripts/provision-gcp.sh`.
- `make deploy` → source-based Cloud Build deploy:
  `gcloud run deploy $SERVICE --source . --add-cloudsql-instances <conn> --set-secrets ...
--set-env-vars-file .env.cloudrun.yaml --region ... --project ...`.
- `make migrate` → start **Cloud SQL Auth Proxy** locally, point `DATABASE_URL` at
  `127.0.0.1`, run `drizzle-kit push --force` then `psql -f drizzle/rls_policies.sql`, stop
  proxy. (Auth Proxy because Cloud SQL is not publicly reachable; auto-download the proxy if
  missing.)
- `make domain` → `gcloud run domain-mappings create --service ... --domain <client-domain>`;
  print the CNAME for the client's DNS.

Keep the existing `Dockerfile` as-is (already Cloud Run-ready).

## Decisions & assumptions

- **Storage stays Cloudflare R2 for now** (you only specified DB → Cloud SQL). Correction to the
  original draft: there is **no existing `STORAGE_PROVIDER` abstraction** — `src/lib/storage`
  is hardcoded to R2. Moving storage into the client's GCP (GCS) is a real follow-up that means
  building the provider abstraction first, not a config swap. Flagged, not in scope.
- **Migrations run via Cloud SQL Auth Proxy** from the operator machine (simplest). Can be
  upgraded to a Cloud Build/Cloud Run migration job later for CI.
- **One repo, many deployments** — per-client config lives in gitignored `.env` files, not
  branches. (If you'd rather fork a repo per client, the same scripts still work.)
